# Generator specification

## Boundaries

A stack adapter receives a normalized project snapshot, versioned inputs, and explicit capabilities. It emits deterministic planned file operations and diagnostics. The pure planner is reusable by Electron and a future CLI. Main-owned filesystem and Git adapters take snapshots and apply approved plans. Templates are data in a restricted deterministic renderer. Pin the engine, stack adapter, templates, module graph, and schema input versions.

The first delivered generator scaffolds a clean repository using the Node.js, TypeScript, Express, React, Vite, and PostgreSQL combination. Workspaces with existing files remain inspectable. Phase 05 adds append-only source migration creation through a journal and optional CRUD in a new project. Phase 06 supports reviewed incremental CRUD generation in compatible managed projects. The second stack uses idiomatic Go and Gin structure and validates the same lifecycle in Phase 08.

## Lifecycle and evidence

| Stage | Output or guard |
| --- | --- |
| Inspect | Canonical workspace grant and scan revision, Git common directory, full branch ref and commit or explicit non-Git state, metadata versions, and fingerprints of inputs and candidate destinations. |
| Plan | Immutable ordered operations with normalized relative paths, expected absence or before digest, after digest, readable before/after diff, ownership, and optional prerequisites. Preserve human-authored files. |
| Validate | Check stack compatibility, module graph, schema constraints, output boundaries, collisions, destination permissions, file ownership, size, and encoding. Blocking diagnostics prevent approval. |
| Preview | Show creates, edits, conflicts, and any explicitly supported removals, along with the exact review scope and proposed verification. |
| Approve | Main binds approval to the plan digest, workspace grant, revision and operation identity. Invalidate approval on input changes, workspace switch, or a relevant external change. |
| Apply | Under the worktree lock, revalidate identity, branch, commit, relevant files and parent directories. Persist the recovery record before applying the planned writes. |
| Verify | Read back files and digests, validate generated metadata, report expected outputs and failures. Dependency installation, script execution, and physical database checks require their own authorization. |

Normalize deterministic input ordering and line endings for generated content. Hash exact bytes with SHA-256 and use a stable encoding for structured input digests. Generated bytes and manifests must match for identical complete inputs, including the same explicit project ID. Exclude clocks, absolute locations, network data, credentials, and runtime randomness from rendering. Persist the plan's input digests, template identifiers, ownership, and expected fingerprints.

## Overwrite protection

Initial generation requires an empty admitted directory, a new child authorized under a selected parent, or an explicitly admitted clean Git directory containing only allowed administrative entries. Include creation of a new destination in the plan and recovery journal. Use exclusive creation semantics for new directories and files. A collision creates a conflict and requires a new reviewed plan. Incremental generation may update an existing managed file only while its recorded baseline and current bytes agree, or when a stack-aware adapter can prove a reviewed edit is limited to its owned extension point and preserves custom content. Supply exact new bytes for review. Refuse ambiguous markers, unsupported syntax, unknown files, or uncertain ownership. Prefer generated sibling files, narrow extension points, and stack-aware parsing for routes and registrations. Detect platform path collisions, parent link replacement, root movement, external edits, and stale plans at write time.

The manifest records relative paths, owner module or template, generator version, and before/after fingerprints where relevant. The planned operation binds each destructive change to a distinct review choice. Do not use implicit overwrites, automatic three-way business-logic resolution, or destructive cleanup to finish a generation run.

## Recovery

Use a durable operation journal with workspace identity, plan digest, intended operations, prior file digests and backups, staging locations, and per-step state. Stage validated payloads on the target filesystem. Flush the journal before replacing or creating files, update it after verified steps, and record final manifest publication. Multi-file operations remain recoverable across interruption. Use verified replacement and exclusive creation primitives appropriate to the target OS.

If apply fails or startup detects an incomplete record, mark the workspace recovery-required. Block overlapping generator and Git writes. Offer inspected Resume, Roll Back, or manual handoff where safe. Compare live content to recorded before and after fingerprints before changing anything, preserve intervening user edits, and surface conflicts for manual recovery. Verify final digests and release locks only after the state is consistent. Bound backup retention, restrict access, and keep secret contents out of logs. Test interruption before and after every journal/write boundary, including Windows sharing violations, symlink or junction changes, and concurrent external modifications.

## Generated application boundaries

Initial outputs include normal application source, build scripts, lockfiles, environment variable documentation, tests, and a PostgreSQL migration workflow. Phase 04 verifies a working PostgreSQL-backed feature using an isolated database. Phase 05 owns schema reconciliation. Phase 06 extends reviewed CRUD generation to eligible files in existing projects, including ownership-aware application source edits and conflict handling. Templates and module dependencies expand in Phase 07. Deployment artifacts join a reviewed release workflow in Phase 11. The [SDK](STACK_PLUGIN_SDK.md) describes stack ownership and compatibility.

## Phase 04 project instructions

The first stack plan includes an ordinary `AGENTS.md` and README with the supported commands, layout, local configuration keys without values, ownership rules, and reviewed migration workflow. Generate them deterministically from the pinned stack profile. Preview their paths and changes and apply the same collision, stale review, and recovery rules as source files. Existing user instructions remain owned by their author unless the reviewed plan identifies an authorized edit. An AI provider, runtime agent, and executable project context are outside this scope.

## Phase 04 implementation decisions

The initial wizard authorizes one absent child of a native-selected parent outside an existing Git worktree. Existing folders, Git initialization and incremental edits are separate operations. The immutable plan binds one explicit project UUID, normalized name, folder/package slug, API port, the selected built-in profile versions, and exact file bytes. Main retains the plan and consumes the opaque approval token. The native confirmation identifies the target and SHA-256 digest. Every intended write is create-only.

The portable descriptor identifies the project and stack. The version lock records the built-in template digest, the Layered Web architecture profile and Standard Engineering profile versions. The manifest records the exact SHA-256 of all baseline outputs except itself. The reviewed plan digest and final read-back also cover the manifest.

Before writing, main flushes an app-data recovery record containing the approved plan identity and destination grant. It creates each directory exclusively, stores its identity, stages each file in its checked destination directory, flushes the staged bytes, and publishes with a same-filesystem hard link that fails if the target exists. After read-back, Studio removes the staged name and checkpoints progress. The final verification compares all names and bytes before closing the journal. Hard-link support is required on the destination filesystem.

Recovery requires native reselection of the original parent and explicit approval after a restart. Studio verifies recorded directory identities and regenerates the exact reviewed plan. It preserves conflicts and incomplete or ambiguous staging files for manual review. Phase 04 offers resume and manual handoff. Close Record ends automatic recovery after native confirmation and leaves every project and staging file in place. Rollback or deletion of project output is outside this phase. Overlapping Git writes are blocked while the journal is pending.

Linux anchors file operations to an opened directory via procfs. Windows uses opened directory identity and checks canonical paths around native operations, with exclusive file publication and verification. These checks detect changed paths and refuse recovery against replacement directories. On platforms without descriptor-relative writes in Node, the path check and syscall retain a same-user concurrency window. A Windows native sandbox or handle-relative write API would be required to isolate actively racing desktop processes.

Desktop verification covers file integrity and successful admission. Installs, tests, application startup and database commands run independently in disposable fixtures and in the user's terminal. The wizard never installs dependencies, starts the project or connects to its database.

## Phase 04 modular configuration

New previews validate the full-stack Node.js / PostgreSQL combination and a bounded list of module selections. Each selection contains an ID and exact version. The shared catalog records availability, compatible application types and databases, and required module IDs. Validation rejects duplicate, unknown, unavailable, incompatible, wrong-version and missing-prerequisite selections. No project supplies a template path, package name, registration code, or executable hook.

The default foundation owns liveness, PostgreSQL readiness, the checksummed migration ledger, runtime dependencies, and engineering standards. It creates no domain tables. The optional Welcome example owns its API route and controller, repository, service, React panel, SQL migration, and test. It reuses the foundation's dependencies. Trusted template contributions are assembled during planning and compose registrations, test commands and project instructions. Only selected contributions are rendered. New manifest v2 entries track file ownership. The version lock and the module lock capture selected versions, contribution digests and prerequisites. Case-insensitive file collisions and file-versus-directory conflicts are rejected before approval.

The v1 template inventory and hash layout remain available for previously approved recovery records. They cannot be requested by new previews. Existing generated repositories remain standalone and receive no automatic conversion.

Backend-only, frontend-only and database-free shapes are represented as future choices and remain unavailable. Authentication, user management, RBAC, audit logging, reporting, Excel, files, notifications, scheduling, and payments are planned. The planned auth dependency relationship is authentication requiring user management, with RBAC requiring both. The Phase 06–07 library owns installation into existing projects, version resolution beyond the initial exact pins, and full graph validation.


## Phase 05 create-only configuration

The Node starter accepts an optional version 1 PostgreSQL schema and two explicit table selections for backend and frontend. Every selected frontend table requires a selected backend table. The new project includes its schema migration; select no CRUD tables to generate the migration and schema documentation alone. Backend CRUD supports a single primary key of smallint, integer, text or UUID with compatible columns (smallint, integer, text, UUID, boolean and date). Composite keys and additional types remain available for schema-only designs. API queries use bound values. HTTP models, validation, repositories, services and controllers are generated only for selected tables. The React table, editor and delete confirmation are emitted only when page selection is enabled. The generated routes require appropriate deployment access controls.

The initial generation plan owns the schema and CRUD files under the pinned PostgreSQL adapter. Fingerprints, selected features and migration location are recorded in the existing portable manifest and version lock. The ordinary frozen dependency graph is reused. Existing managed projects can publish a new migration through Database Studio. Studio cannot replace their API, UI, tests or documentation during Phase 05. Phase 06 adds reviewed file-level ownership and conflict handling for incremental installation or updates.


## Phase 06 incremental CRUD

Generation Review supports modular v2 Node / PostgreSQL starters with the pinned Layered Web and Standard Engineering profiles. It reads the admitted worktree, checked-out refs, descriptor, version lock, generation manifest and migration history. The registry maps known built-in files to their original owners. Reading ordinary project entries for inventory never adopts them. V1 starters and unsupported locks are reported without writes.

The declared source is the current ordered PostgreSQL migration history. Incremental generation combines existing CRUD selections with the new compatible table selections, resolves the old schema from locked source fingerprints, and composes built-in files through the same generator used at project creation. It emits no SQL migrations, does not alter the dependency graph, and does not connect to databases. The UI reports externally authored sources and exact checksums. Repeated unchanged previews have zero writes.

The planner reconstructs the published built-in route, React and package integrations from pinned templates. It offers whole-file replacement only when the exact old template bytes and manifest fingerprint agree with the worktree. This keeps the extension mechanism reviewable and avoids parsing or rewriting customized code. Known untouched feature files, custom services and application documents are preserved. A missing, unowned or modified required integration is a conflict. Generated API and schema guides plus the manifest and version lock record selected layers and source provenance. Manually written instructions and requirements remain user-owned.

Main keeps the exact plan and checks the worktree grant, Git identity, branch, commit, relevant status, staged paths, source bytes and parent identities twice around the native approval. Apply retains before and after bytes in a bounded app-data journal. For each approved replacement it moves the verified original to a same-directory recovery name and publishes the reviewed new bytes via the existing exclusive hard-link operation. It publishes the manifest last and verifies the entire plan before clearing the checkpoint and recording a receipt. Recovery requires a new native confirmation and validates every target, parent and saved artifact before continuing. Handoff preserves existing files and recovery artifacts. A directory created immediately before its identity can be journaled can require manual inspection. Source recovery, Git and database recovery are independent.

Recovery stays visible after the same directory is reopened at a different path. Resume requires the original approved path and unchanged context. A handoff preserves any sibling file whose name starts with `.factory-incremental-backup-` or `.factory-incremental-stage-` followed by the displayed operation ID.


## Phase 07 engineering assets

Compose reviewed bundled module releases in dependency order. Required modules must be explicitly selected. The lock pins the architecture, executable template, engineering snapshot and module contribution fingerprints. Persist a declarative profile and optional business-template branding in .factory/engineering.json. Generate the engineering guide from the profile's typed topics, and keep client requirements separate. The wizard preview contains exact SQL and generated instructions. Foundation output without new options retains its prior bytes.

Incremental module installation adds only eligible bundled identity revisions. It requires pristine required integration entrypoints and managed locks, appends a versioned migration sequence after current source, proves the prospective SQL model and uses the existing recoverable filesystem writer. Migration publication never executes SQL. Repeated installation of the same releases has zero writes. Module removal and module upgrades are unavailable.

## Phase 08 stack resolution

The closed catalog resolves exact stack and architecture identifiers before rendering. Its Go Service v1 adapter emits Go commands and internal packages, dependency checksums, React/Vite, and stack-specific instructions. Legacy Node plans retain their existing configuration and byte layout. PostgreSQL migration composition, renderer contracts, file fingerprints, approval and journaling are shared. Verify generated files in Studio and run project tools separately. Studio never invokes either stack's runtime from preparation, preview, recovery or project inspection.

Incremental Go CRUD reconstructs the pinned Go baseline and schema history, uses the same supported file ownership transitions as Node, and stages changes after native consent. Go module, HTTP integration, and active frontend integration must match the prior generator baseline. Independent customized services can remain unchanged when a change needs no edits to them. Existing SQL stays in place.

## Linked worktree context

Linked previews bind the common and checkout metadata identities, branch, HEAD, and the existing workspace grant. File ownership, portable locks and receipt state come from the selected checkout. Changing branches or reviewed source files invalidates the approval. A Git transition affects source files and leaves database application to its own reviewed workflow.

## Phase 10 design publication

The incremental planner accepts a closed developer-design selection in place of CRUD or module inputs. It records artifact references in a versioned portable document. Page publication has fixed built-in paths and verifies the exact pinned Vite preimage, absent outputs, compatible template, reviewed endpoint provenance and existing project ownership. The plan lists all generated and modified bytes. It adds output fingerprints to the same manifest and uses the existing exclusive transaction, journal and recovery UI. This release creates one unauthenticated Node.js page entry. Arbitrary layout and integration rewriting are outside its capability.
