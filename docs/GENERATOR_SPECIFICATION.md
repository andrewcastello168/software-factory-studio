# Generator specification

## Boundaries

A stack adapter receives a normalized project snapshot, versioned inputs, and explicit capabilities. It emits deterministic planned file operations and diagnostics. The pure planner is reusable by Electron and a future CLI. Main-owned filesystem and Git adapters take snapshots and apply approved plans. Templates are data in a restricted deterministic renderer. Pin the engine, stack adapter, templates, module graph, and schema input versions.

The first delivered generator scaffolds a clean repository using the Node.js, TypeScript, Express, React, Vite, and PostgreSQL combination. Workspaces with existing files remain inspectable. Phase 05 adds append-only source migration creation through the journal. Incremental application source generation arrives in Phase 06. The second stack uses idiomatic Go and Gin structure and validates the same lifecycle in Phase 08.

## Lifecycle and evidence

| Stage | Output or guard |
| --- | --- |
| Inspect | Canonical workspace grant and scan revision, Git common directory, full branch ref and commit or explicit non-Git state, metadata versions, and fingerprints of inputs and candidate destinations. |
| Plan | Immutable ordered operations with normalized relative paths, expected absence or before digest, after digest, readable before/after diff, ownership, and optional prerequisites. Preserve human-authored files. |
| Validate | Check stack compatibility, module graph, schema constraints, output boundaries, collisions, destination permissions, file ownership, size, and encoding. Blocking diagnostics prevent approval. |
| Preview | Show creates, edits, conflicts, and any explicitly supported removals, along with the exact review scope and proposed verification. |
| Approve | Main binds approval to the plan digest, workspace grant, revision and operation identity. Invalidate approval on input changes, workspace switch, or a relevant external change. |
| Apply | Under the worktree lock, revalidate identity, branch, commit, relevant files and parent directories. Persist the recovery record before applying the planned writes. |
| Verify | Read back files and digests, validate generated metadata, report expected outputs and failures. Dependency installation, script execution, and physical database checks require their own authorization. |

Normalize deterministic input ordering and line endings for generated content. Hash exact bytes with SHA-256 and use a stable encoding for structured input digests. Generated bytes and manifests must match for identical complete inputs, including the same explicit project ID. Exclude clocks, absolute locations, network data, credentials, and runtime randomness from rendering. Persist the plan's input digests, template identifiers, ownership, and expected fingerprints.

## Overwrite protection

Initial generation requires an empty admitted directory, a new child authorized under a selected parent, or an explicitly admitted clean Git directory containing only allowed administrative entries. Include creation of a new destination in the plan and recovery journal. Use exclusive creation semantics for new directories and files. A collision creates a conflict and requires a new reviewed plan. Incremental generation may update an existing managed file only while its recorded baseline and current bytes agree, or when a stack-aware adapter can prove a reviewed edit is limited to its owned extension point and preserves custom content. Supply exact new bytes for review. Refuse ambiguous markers, unsupported syntax, unknown files, or uncertain ownership. Prefer generated sibling files, narrow extension points, and stack-aware parsing for routes and registrations. Detect platform path collisions, parent link replacement, root movement, external edits, and stale plans at write time.

The manifest records relative paths, owner module or template, generator version, and before/after fingerprints where relevant. The planned operation binds each destructive change to a distinct review choice. Do not use implicit overwrites, automatic three-way business-logic resolution, or destructive cleanup to finish a generation run.

## Recovery

Use a durable operation journal with workspace identity, plan digest, intended operations, prior file digests and backups, staging locations, and per-step state. Stage validated payloads on the target filesystem. Flush the journal before replacing or creating files, update it after verified steps, and record final manifest publication. Multi-file operations remain recoverable across interruption. Use verified replacement and exclusive creation primitives appropriate to the target OS.

If apply fails or startup detects an incomplete record, mark the workspace recovery-required. Block overlapping generator and Git writes. Offer inspected Resume, Roll Back, or manual handoff where safe. Compare live content to recorded before and after fingerprints before changing anything, preserve intervening user edits, and surface conflicts for manual recovery. Verify final digests and release locks only after the state is consistent. Bound backup retention, restrict access, and keep secret contents out of logs. Test interruption before and after every journal/write boundary, including Windows sharing violations, symlink or junction changes, and concurrent external modifications.

## Generated application boundaries

Initial outputs include normal application source, build scripts, lockfiles, environment variable documentation, tests, and a PostgreSQL migration workflow. Phase 04 verifies a working PostgreSQL-backed feature using an isolated database. Phase 05 owns schema reconciliation. Phase 06 adds reviewed generation for supported migrations, models, repositories, services, controllers or handlers, API routes, validation, forms, CRUD pages, tables, tests, and docs. Templates and module dependencies expand in Phase 07. Deployment artifacts join a reviewed release workflow in Phase 11. The [SDK](STACK_PLUGIN_SDK.md) describes stack ownership and compatibility.

## Phase 04 project instructions

The first stack plan includes an ordinary `AGENTS.md` and README with the supported commands, layout, local configuration keys without values, ownership rules, and reviewed migration workflow. Generate them deterministically from the pinned stack profile. Preview their paths and changes and apply the same collision, stale review, and recovery rules as source files. Existing user instructions remain owned by their author unless the reviewed plan identifies an authorized edit. An AI provider, runtime agent, and executable project context are outside this scope.

## Phase 04 implementation decisions

The initial wizard authorizes one absent child of a native-selected parent outside an existing Git worktree. Existing folders, Git initialization and incremental edits are separate operations. The immutable plan binds one explicit project UUID, normalized name, folder/package slug, API port, the selected built-in profile versions, and exact file bytes. Main retains the plan and consumes the opaque approval token. The native confirmation identifies the target and SHA-256 digest. Every intended write is create-only.

The portable descriptor identifies the project and stack. The version lock records the built-in template digest, the Layered Web architecture profile and Standard Engineering profile versions. The manifest records the exact SHA-256 of all baseline outputs except itself. The reviewed plan digest and final read-back also cover the manifest.

Before writing, main flushes an app-data recovery record containing the approved plan identity and destination grant. It creates each directory exclusively, stores its identity, stages each file in its checked destination directory, flushes the staged bytes, and publishes with a same-filesystem hard link that fails if the target exists. After read-back, Studio removes the staged name and checkpoints progress. The final verification compares all names and bytes before closing the journal. Hard-link support is required on the destination filesystem.

Recovery requires native reselection of the original parent and explicit approval after a restart. Studio verifies recorded directory identities and regenerates the exact reviewed plan. It preserves conflicts and incomplete or ambiguous staging files for manual review. Phase 04 offers resume and manual handoff. It has no deletion or rollback command. Overlapping Git writes are blocked while the journal is pending.

Linux anchors file operations to an opened directory via procfs. Windows uses opened directory identity and checks canonical paths around native operations, with exclusive file publication and verification. These checks detect changed paths and refuse recovery against replacement directories. On platforms without descriptor-relative writes in Node, the path check and syscall retain a same-user concurrency window. A Windows native sandbox or handle-relative write API would be required to isolate actively racing desktop processes.

Desktop verification covers file integrity and successful admission. Installs, tests, application startup and database commands run independently in disposable fixtures and in the user's terminal. The wizard never installs dependencies, starts the project or connects to its database.
